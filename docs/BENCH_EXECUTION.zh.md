# Mini Bench 内部账号路由

[English](BENCH_EXECUTION.md)

同一供应商的两个账号可以分别建路由，再用同一模型、题库和 Thinking 跑对比。路由保存在 Mini Bench 自己的配置文件里，不创建或修改 Magpie 供应商，不切换全局登录账号。CLI 与 `/api/bench/` 共用一个后台调度器。

## 直接使用 Magpie 模型

在 Magpie 插件中，没有设置 `MAGPIE_BENCH_ROUTES_FILE`，且数据目录下没有 `routes.json` 时，适配器从宿主 Magpie 的模型目录生成测试目标，沿用宿主网关地址和凭证，无需为每个模型手写配置。只列出明确提供有限、非负输入和输出 Token 单价的模型，缺失价格不按免费处理。Thinking 档位来自模型目录。

目录提供有效的 `owned_by`、`display_name` 时，公开路由分别保留为可选的 `provider_id`、`model_display_name`，供应商声明附带 `provider_evidence: "gateway_catalog"`。`provider_id` 标识目录归属实例，不是供应商类型，也不证明最终响应请求的上游服务商。不同实例即使提供同名模型也保持分开。界面不拆解模型 ID 或展示名称来推断身份，公开目录不提供权威的供应商类型和图标时使用中性图标。计划和结果保存当时记录的元数据，历史观测没有记录的字段返回 `null`，不从当前目录回填。显式路由配置仍使用原有严格字段，不需要新增元数据配置。

自动分配目标共享 `gateway-default` 并发池，结果标为 `gateway_binding`，不能据此判断真实上游账号。对于本机 Magpie 的非远端渠道，插件会自动发现接收端网关上的具名本地账号与多 Key（`gateway_account_binding`），并支持通过 [`accounts` 选项](../magpie/README.zh.md#本地多账号与多-key-绑定)补充或覆盖（`configured_binding`），由适配器设置 `X-Magpie-Account` 固定请求头；远端额度卡片不会生成固定账号路由。独立运行的 Mini Bench 使用下文的显式路由，不会自动连接 Magpie。

适配器缓存模型目录最长 60 秒，并合并并发读取；刷新路由会使缓存过期。已删除的模型不能继续解析，已启动运行则保留原绑定和快照。目录故障不影响打开历史结果或取消运行。目录读取不发模型请求，重复模型 ID 会报错，不会静默选择其中一组价格。

显式路由配置始终优先：配置文件内容为 `{"routes": []}` 或显式指定的文件不存在时，目标列表保持为空，不自动改走默认网关；路径环境变量为空或文件格式损坏会报错。密钥仅保留在服务端，UI 不接收上游地址或凭证。

### Remote Magpie 路由展开

目录提供有效的 `magpie_via` 证据时，选择器自动展开 Remote Magpie 后面的路由。服务通过受支持的目录请求头 `X-Magpie-Drawers: 1` 获取这项证据，并排除该请求额外返回的图片模型及其他非对话模型。

对于 `office/openai/model` 这样的直接远端条目，渠道列显示 `office / openai`。`office` 仍是本地目录归属，`openai` 是第一级远端**路由命名空间**，不是已核验的服务商身份。远端的 `auto`、`group` 分别标为自动路由和路由组。不同本地远端实例即使内部目录同名也不会合并。只展开一级，后续斜杠可能属于模型名，不递归推断。

公开路由、计划和新结果保留 `remote_route: {"namespace": "openai", "evidence": "magpie_via_catalog"}`。完整请求模型名及路由 ID 不变，账号仍保持未知。缺少或无效的跳转证据、本地路由组，以及未记录这项元数据的旧结果，都保留原有分组；不会回填历史记录，也不会把每进程随机生成的 hop ID 保存为稳定身份。路径约定见 Magpie 的[远端路由文档](https://usemagpie.ai/docs/remote)。

任务选择器展示供应商、已记录或已固定的账号、模型和 Thinking 档位，前端不展示或请求额度。远端与未固定路由的账号身份保持未知，历史结果不回填。

## 配置两条路由

示例见 [`benchmark/examples/bench-routes.json`](../benchmark/examples/bench-routes.json)。将它复制到 `~/.local/share/magpie-mini-bench/routes.json`，也可通过服务进程的 `MAGPIE_BENCH_ROUTES_FILE` 指向其他文件。建议文件权限为 `0600`。路由配置在第一次访问新执行服务时加载，修改后需要重启服务。

每条路由绑定以下字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定路由 ID，供执行计划引用 |
| `label` | 展示名称，不是账号验证证据 |
| `account_ref` | 共享账号并发池的稳定标识，同一个账号的多个模型应使用相同值 |
| `base_url` | 支持 Responses API 的上游地址，可直连供应商或使用账号限定的网关 |
| `model` | 发送给上游的精确模型名 |
| `api_key_env` | 服务进程中的密钥环境变量名，配置文件不接收明文密钥 |
| `thinking_levels` | 本地明确声明支持的档位，空数组时界面只提供 `default` |
| `pricing.prompt` / `pricing.completion` | 每个输入／输出 Token 的美元价格，不是每百万 Token 价格 |
| `account_concurrency` | 该账号在所有新 Mini Bench 任务中共享的样本并发上限 |

示例地址、模型、价格和 Thinking 档位都需要替换成实际值。比如每百万输入 Token 为 1 美元时，`pricing.prompt` 应填 `0.000001`。只有确认免费时才填零，不要用零代替未知价格。

两个账号分别使用 `BENCH_PROVIDER_ACCOUNT_A_KEY` 和 `BENCH_PROVIDER_ACCOUNT_B_KEY`。这些变量必须存在于运行后端的进程环境中，仅在启动 CLI 的终端设置并不会传给已经运行的插件。不要把密钥写进计划、项目文件或命令参数。

远程上游必须使用 HTTPS，HTTP 仅允许 loopback。模型请求不跟随 HTTP 重定向。只支持 `/v1/responses`，不会自动回退到 Chat Completions 或其他账号。

### 账号绑定不等于上游身份已核验

`account_ref` 是你配置的身份，不是从模型回答中识别出的账号。执行结果使用 `configured_binding` 表示绑定来源，不标记为已核验。同一个真实账号的两把 Key 应使用相同 `account_ref`，两个不同账号才分别命名。

如果上游仍是一个自动轮换账号的网关，两条本地路由并不会把它变成固定账号路由。本机 Magpie 的账号可以通过插件的显式 `accounts` 选项固定；其他网关需要其支持的账号限定凭证或适配器。不能只把邮箱填进 `account_ref` 就认为完成绑定。本版本不自动登录、不签发 Magpie Key，也不核验上游实际账号。响应 ID 和原始响应会保留，供后续核对。

## 任务与独立运行

一个任务包含多个独立运行，每个选中的路由和 Thinking 组合生成一个运行，分别保存执行 ID、进度、预算、样本和结果。渠道、账号和模型绑定由路由提供，选择一个展示名称不会增强身份凭据。每次运行执行完整 Mini Bench 题库，默认 3 轮、运行内样本并发 6、任务内运行并发 3。选择 7 个组合就会生成 7 次运行，每次 36 个样本，共 252 个样本。

```json
{
  "bank_version": "1.0",
  "targets": [
    {"route_id": "provider-a-model-x", "thinking": "none"},
    {"route_id": "provider-a-model-x", "thinking": "high"}
  ],
  "rounds": 3,
  "sample_concurrency": 6,
  "run_concurrency": 3,
  "limits": {"timeout": 600, "timeout_scope": "sample"}
}
```

将上述结构保存为任务计划，用 `task-plan FILE` 预检，核对后用 `task-start FILE` 提交。`tasks`、`task-show TASK_ID`、`task-cancel TASK_ID` 管理整批任务；`show RUN_ID`、`cancel RUN_ID` 查看或取消单个子运行。CLI 和 UI 使用同一个进程内执行引擎，不为每次运行启动 CLI 子进程。

新任务默认 `timeout: 600`、`timeout_scope: "sample"`；`max_requests`、`max_output_tokens`、`max_cost_usd`、`max_turns` 和 `max_tool_calls` 均为 `null`（无上限）。超时覆盖每道题的完整请求、工具交互和重试，不对每个 HTTP 请求重新授时。`total_max_cost_usd` 为 `null`。未记录 `timeout_scope` 的历史运行仍使用原有单请求超时及数字上限，不改写原计划或协议哈希。任务不额外限制总样本数。每个任务独立管理自己的 `run_concurrency` 与 `sample_concurrency`，并把并发子运行交错分散到不同渠道和模型，预算仍按每个运行执行。任务不接收 `task_ids`，少量题目验证仅通过下文的直接运行接口执行。提交超时后先查看 `tasks` 和 `runs`，不要直接重复提交。

所有子运行的归属关系提交成功后才允许调度。每个子运行有独立快照和日志，`assessment/tasks/<task_id>/task.json` 保存任务归属。可以取消单个子运行，也可以取消整个任务。重启后未完成的工作标记为中断，不自动续跑。历史多目标运行保持可读，不改写成新任务。

## 预检与直接运行

启动后端沿用 [README](../README.zh.md) 的插件安装方式。使用显式账号路由时，先完成配置和环境变量设置，再启动或重启。不要同时启动多个进程操作同一数据目录，各进程的并发额度也不会共享。

以下 CLI 命令从仓库根目录运行。CLI 连接已经运行的本地服务，默认地址为 `http://127.0.0.1:3481`。通过 `--url` 或 `MAGPIE_BENCH_URL` 更改地址，使用 `MAGPIE_BENCH_TOKEN` 认证。

```sh
bun benchmark/bench.ts routes
bun benchmark/bench.ts banks
bun benchmark/bench.ts plan benchmark/examples/bench-plan.json
bun benchmark/bench.ts start benchmark/examples/bench-plan.json
bun benchmark/bench.ts runs
bun benchmark/bench.ts show <run_id>
bun benchmark/bench.ts cancel <run_id>
```

[`benchmark/examples/bench-plan.json`](../benchmark/examples/bench-plan.json) 包含两个账号，各跑 `none`、`high` 两个档位。完整 12 题、1 轮，共 48 个样本。省略 `task_ids` 表示完整题库，也可以显式选择少量题目验证配置：

```json
{
  "bank_version": "1.0",
  "targets": [
    {"id": "a-high", "route_id": "provider-a-model-x", "thinking": "high"},
    {"id": "b-high", "route_id": "provider-b-model-x", "thinking": "high"}
  ],
  "task_ids": ["K23_HTTP_Conditional_Cache_Precedence"],
  "rounds": 1,
  "concurrency": 2,
  "limits": {"timeout": 600, "timeout_scope": "sample"}
}
```

`plan` 验证配置、凭证引用和执行规模，不发模型请求。`start` 重新校验并保存快照，立即返回运行 ID，执行不依赖 CLI 保持打开。提交超时不能证明任务未创建，应先查看 `runs`，不要直接重复提交。当前没有提交去重键。

目标的 `thinking` 可选：省略或 `default` 时不发送 `reasoning`，与显式 `none` 不同；其他值必须是路由声明的档位，以 `reasoning.effort` 发送；`mixed`、`unknown` 为保留值。新计划只配置 `timeout` 和 `timeout_scope: "sample"`；旧上限字段仍可读取，以保留历史记录及显式旧 API 客户端的语义。显式路由的 Thinking 档位来自本地声明，默认网关路由则取自目录；两者都不会通过模型请求探测能力。

### 不通过插件运行

TypeScript 后端和网页位于 `benchmark/`，可通过 Bun 独立运行，不依赖 Magpie 适配器。在服务进程环境中，将 `MAGPIE_BENCH_TOKEN` 设置为至少 32 字符的随机字符串；独立服务需配置显式路由及其密钥环境变量，或由嵌入方注入适配器。从仓库根目录启动：

```sh
bun benchmark/bench.ts serve --port 3481
```

服务提供 `benchmark/web/` 网页和同一套 HTTP API，CLI 仍通过 `MAGPIE_BENCH_TOKEN` 认证。不要与已启用的插件同时占用相同端口或数据目录。持久运行时使用受管理的 tmux 任务，并明确完成或失败通知方式。

## 调度与结果

所有 Mini Bench 任务和运行共用一个调度器。每个任务独立控制自身的 `run_concurrency`（1 到 10，默认 3）与 `sample_concurrency`（1 到 64，默认 6），不与其他任务互相排队等待；任务子运行可以并发执行固定目标的多个样本，且子运行按渠道和模型交错调度，使并发槽位优先分散在不同渠道和模型，而不是集中到同一渠道的多个 Thinking 档位。通过 `/runs` 创建的直接运行共享全局上限 `MAGPIE_BENCH_CONCURRENCY`（1 到 64，默认 18）、同账号并发上限（同一账号的不同 Thinking 和模型共享额度）以及每个目标最多一个样本的限制。空闲槽位直接补入可执行样本，不等待整批结束。

一个样本对应目标、题目和轮次，工具题的多次请求在该样本内顺序执行，工具状态不跨样本共享。样本和实际尝试分别保存 ID，同模型、不同账号不会覆盖。原始响应先于评分保存，API 失败及缺失、不可评分结果不记作零分。整题超时（`SampleTimeout`）按 `0` 分计，运行仍可完成为 `completed` 且保留手动重试资格。分析页仅从符合条件的记录计算[已定义的得分费用展示指标](ASSESSMENT_BANK.zh.md#得分费用图)，不改变保存的评分。

新任务记录每次请求作为证据，但只执行整题总超时，所有请求、工具交互及重试等待共用截止时间。手动重试历史运行仍遵守原记录中的请求及费用上限。传输异常、HTTP 408/429/5xx，以及 HTTP 200 流式响应以 `response.failed` 且错误码为 `server_error` 结束（如网关中途断连）或为限流/额度错误码（`rate_limit_exceeded`、`insufficient_quota`，按 HTTP 429 处理），默认在首次请求后最多重试 3 次，由 `max_api_retries` 控制，采用指数退避并遵守有界的 Retry-After。认证及其他永久性 4xx 不自动重试。快速失败：若某样本以 API 失败结束（或提交有效答案后上游中断），且最后一次响应为 HTTP 429 或流式 `response.failed` 且错误码为 `rate_limit_exceeded`/`insufficient_quota`（`rate_limited`）、401/403（`access_denied`）、402（`payment_required`）或 404（`model_not_found`），整个服务不再为该路由（同一模型及账号绑定）启动新样本，包括同一运行、同任务其他 Thinking 子运行、并发中的其他任务以及之后新建的任务；已在执行的样本照常结束。其他路由不受影响，包括同渠道其他账号和自动路由组（各自有独立路由 ID）。只需一个这样的样本即触发。样本内的 API 重试已覆盖临时异常，因此封禁不会自动解除，均持续到对该路由的运行显式手动重试（会解除封禁）或服务重启。未发送的样本记为 `budget_not_admitted` 并带上述停止原因，不计零分，可手动重试。超时、5xx 和传输异常不会触发快速失败。输出、工具或交互上限等能力问题记为 `incomplete`（未完成）；API 重试耗尽后样本记为 `api_failure`，运行记为 `failed`。缺失用量和费用保持 null，并保守预留可能费用，不因某次错误响应未带用量而直接停止所有后续样本。工具请求不设置 `parallel_tool_calls`。同一响应中的多个函数调用会先验证调用 ID 唯一有效，再按返回顺序运行固定模拟器，逐个持久化结果，最后一次性返回所有对应输出。取消、整题超时或存储失败会停止剩余操作。该执行变化由执行源码快照及 `tool_execution_policy: "ordered-batch-v1"` 记录，不回写旧调用或结果。不会切换账号。上游网关可能内部重试，目前未验证到 Magpie 向插件提供关闭所有此类重试的方法。一条已记录的网关请求不能证明只有一次上游尝试。

评测请求使用 Responses SSE，明确发送 `stream: true`，并记入逐题请求协议及其哈希。完整 SSE 帧先于解析、工具执行和评分写入日志。每条 `stream_chunk` 只记录调用 ID、样本 ID、尝试 ID、序号、时间和帧文本。流片段拼接后与收到的完整流逐字节一致时，调用记录改存 `raw_stream_chunks: N`，不再重复保存全文（可用 `journal_raw_response_text` 还原）；不一致时（如中途中止或 HTTP 错误正文）仍保存 `raw_response_text`。历史日志保持原格式。调用记录保留 HTTP 状态、首末字节时间、首事件及首次输出时间、最近输出进度和终止事件。心跳不计为输出进度，只有完整终止响应中的回答、工具调用和用量才用于后续处理。流提前关闭、SSE 格式错误及成功状态下的非流式响应均记为协议异常，不静默降级为非流式。如果事件持续抵达客户端，流式可能避免网关空闲超时，但不能绕过网关总时限。本地 `SampleTimeout` 或仍然活跃的流都不能证明模型在整个时限内持续计算。历史记录保留原传输协议。

取消会阻止尚未开始的样本及工具后续请求，并中止正在读取的流。中止连接不能证明上游停止计算，也不能保证不计费，已收到的证据会尽量保留。服务重启后，中断的运行不会自动重发请求。可通过运行或任务重试端点显式重试已结束的失败、超时、已中断、已取消或符合条件的 `budget_not_admitted` 样本，必须提交 32 位小写十六进制 `request_id`。同一标识重复提交幂等，适用于响应不确定后的核对。重试前归档原运行字节、调用及源码快照；已完成样本不重跑，重试样本在 `attempts` 中保留历次尝试，最新结果替代失败结果而非取最佳；当最新尝试完成并返回已知用量与费用时，将其作为该样本的有效用量与费用。原路由、账号、价格及剩余执行上限必须仍有效。重试后更新任务摘要、结果和分析。手动重试后的运行只要每次重试批次保持当前题库/判分/模拟器源码哈希、协议限额和执行策略一致，且每题执行协议与评分证据完整，仍可设为完整基线；若重试改变了限额、重跑策略或题库源码，则仅保留用于分析，不能设为基线。

工作区状态——任务、运行、样本、不可变尝试历史、Pi Session 风格的 `session_events`、按内容去重的题库与源码哈希快照及个人基线——统一保存在数据目录下的单个私有 SQLite 数据库（`mini-bench.sqlite`，WAL 模式）中，不再写入原始 SSE 流切片或逐次复制 `source/*.ts`。HTTP 服务同时缓存 `/api/bench/banks`、`/api/bench/tasks`、`/api/bench/runs`、`/api/bench/observations` 以及终态 `/api/bench/runs/:id` 详情响应的序列化及 gzip 结果（有界 LRU，状态或 `updated_at` 变化时自动失效）；`/api/bench/tasks/:id` 和 `/api/bench/runs/:id` 支持 `?omit_provenance=1`，在前端只需展示进度与样本结果时跳过不可变题库与源码快照。

写盘失败时，服务停止接收新请求，释放已结束样本的并发槽，并在内存中标记 `storage_error`。磁盘不可写时无法保证保存这次错误，重启会按最后成功保存的状态标记中断。修复存储问题并重启后才能提交新任务，不应通过重复提交来绕过故障。

新执行源码快照包含执行器及其本地导入依赖，也包含题库加载器无条件导入、但本次未选用其题目的模块。源码路径相对于 `benchmark/` 解析。归档范围不改变题库哈希、评分或历史快照。

新结果保存在数据目录的 `assessment/` 下，包含题目、回答和工具轨迹，应按敏感数据处理。服务不把密钥、密钥环境变量名或上游地址返回给 UI。上游原始内容中已知的凭证字面值会被脱敏，因此保存的响应不是保证逐字节相同的网络报文。

这里只使用 Mini Bench。旧执行器和旧题库 API 已移除，已退役题库的个人数据不会被自动读取、转换或删除。`assessment/` 中的历史 Mini Bench 运行仍可查看，并保留记录时的来源。

## 分析与任务页面

分析页以得分费用图为主。搜索及渠道、模型、Thinking 多选条件直接更新图表；同一条件内取并集，不同条件间取交集，“不限”表示该维度包含全部值。当前条件可逐项移除，“仅此项”只替换所在维度，数据来源条件同时生效。默认“最新数据”按题库及完整/子集范围，在每个渠道、账号、模型和 Thinking 组合内选取记录时间最新的一条，运行与基线分别选取。先选择最新记录，再检查入图资格；最新结果未完成时明确显示未入图，不回退旧成绩。时间未记录的观察因无法判断新旧而保留。“全部历史”显示所有记录（含最新），“指定记录”按精确记录勾选，两种历史模式都可按本地日期筛选，起止日期包含整天。筛选不删除历史、不合并重复评测，也不改变指标。“数据”下拉与渠道、模型和 Thinking 筛选并排，最新/全部/指定模式、日期范围和精确记录勾选都放在面板内，不另起一块表单。匹配记录与未入图数量默认收起，点击后在按钮附近打开限高面板，内部滚动并直接显示原因，不必滚过整张图表。Esc 和关闭操作将焦点还给触发按钮，点击外部也可关闭。支持时使用原生 Popover 和 CSS 锚点，旧浏览器及紧凑窗口使用受视口边界约束的手动定位。分析页浮层统一使用 8px 内边距、紧凑标题行及完成或关闭操作。渠道、模型和 Thinking 筛选分别使用 320px、340px 和 240px 宽度，数据选择为 340px，图表设置为 280px，均受视口宽度约束。图表设置与数据选择共用 Esc、点击外部关闭和焦点返回行为。两种记录面板统一为 440px 宽、最高 360px，窄屏和短窗口进一步缩小。紧凑行保留模型/Thinking、已记录渠道及已知账号声明、本地时间、分数和已知用量，仅未入图行增加原因。长记录 ID、未知账号的重复说明和重复的缺失用量标签不占列表空间，详情中仍保留；跨年份时显示年份，完整时间戳仍可访问。任务和分析共用身份归一化及模型、渠道、账号搜索逻辑。任务选择器用于精确勾选可运行目标，改变候选筛选条件会保留已选目标，点“完成”关闭弹窗；其模型选项跟随当前渠道，切换渠道时保留仍适用的模型条件，否则恢复“全部”。账号仍然可见并支持搜索，不设独立账号筛选。声明了档位的路由只列出这些显式档位；未声明档位的路由只有一个“默认”选项，请求省略 `reasoning`。详情面板保留逐题结果和原始详情，任务历史在任务页搜索和筛选，搜索同时过滤任务与展开任务内匹配的子运行，并提供内联运行预览卡片与原始 JSON 懒加载展开。界面不设独立题库页，选择目标或修改配置时，界面自动更新样本数和合计预算，核对后点击一次“开始评测”即可提交；服务端仍在执行前校验配置，提交成功后自动重置目标选择器的已选项和筛选条件，无需单独生成计划。唯一执行限制配置是每题总超时，默认 600 秒，覆盖请求、工具交互及重试等待；不设置输出 Token、请求数、费用、工具调用数和交互轮数上限。临时 API 错误内部默认重试 3 次。单题超时只结束该样本（按 `0` 分计），继续其他样本。复制旧任务为新任务使用这套新策略，不暗中恢复旧上限。任务及子运行就地展开，提供各状态计数、复制配置和对失败、超时、已中断或已取消样本的手动重试。复制只恢复当前可用的精确目标及设置，不启动请求。提交结果不确定时，须先核对任务历史，再明确允许重新开始，才可再次提交。

重复点击任务或独立运行卡片会切换展开和收起。子运行整行（包括状态文字）切换该运行的样本详情，不关闭父任务；取消按钮不会切换详情。从分析页跳转到运行时始终打开，不会因已展开而收起。轮询保留样本、嵌套原始证据的展开状态及键盘焦点，不会重新打开已主动收起的卡片。

执行完成、评分有效性和用量统计分别展示。已完成样本的 `ambiguous`、`ungradable` 会明确说明无法评分的原因，不再暗示仍在等待评分。解析歧义可能来自不同的候选 JSON 对象，也可能来自额外的损坏 JSON；界面不会自动选取其中一个、重新评分，或将缺失得分补成零分。零分是有效得分。运行摘要提示已完成但无法评分、用量未知或费用未知的样本数量。手动重试完成并返回已知用量与费用后，使用该次有效结果展示，早先尝试仍归档保留；仅当样本有效用量或费用本身未知时，才计入下限展示。

横轴可选每完整 12 题一轮的估算 USD、输入加输出 Token 或每轮耗时。入图要求完整有效得分及所选轴已知非负用量或耗时；缺失 USD 不影响用量或耗时已知的 Token 轴与耗时轴记录。未发出请求的尝试按已知零用量计。得分完整但部分尝试未返回用量时，图表设置“用量不完整时按已知下限绘制”（默认开启）按已知下限绘点。凡含已记录执行异常项（样本超时、提交答案后异常中止 `ended_after_submission`、未调用 `submit_answer` 提交 `no_submission` 或用量不完整）的数据点均带橙色角标（`含异常项`），且不参与帕累托前沿；悬停或固定卡片列出具体异常项，并支持可重试运行直接跳转任务页重试。未入图列表写明具体原因（API 失败、答案歧义、未返回用量的尝试、已中断或已取消等），可重试记录可直接跳到任务页手动重试。运行详情展示逐题逐轮矩阵，优先列出需要关注的样本，并显示从 `/api/bench/runs/:id/calls` 读取的逐次尝试失败原因。“着色”默认选择供应商-模型，保留渠道及账号区分；模型着色让归一化后同名的模型跨供应商同色；模型系列着色按 GPT、DeepSeek 等可识别的名称前缀归组，未识别的模型单独保留。评测时间着色独立于模型选择，按记录的 `created_at` 在查看者本地日期分组，复用同一多色调色板；在已加载的全部观察范围内，日期颜色不因筛选、缩放或切换横轴改变。时间未知用中性色并明确标注。这些归组仅用于显示，不证明实际服务身份。切换着色不合并观察记录、不改变入图资格，也不扩大 Thinking 连线范围。颜色图例在绘图区下方显示一行简览，放不下时可展开限高列表，桌面和窄屏都保持单列。列表保留已记录的渠道、账号信息和数据点数量；搜索只查找图例，不筛选观察记录。悬停或聚焦条目可定位同色数据点，不改变 Thinking 连线范围。图例随横轴、筛选和缩放更新，数量保留所有可见重复观察。切换着色方式会重置图例搜索和展开状态。普通评测用圆点、基线用方块；最新实心、历史空心，时间未知用虚线边框并明确标注状态未知。最新状态从全部观察中确定，先于入图资格和显示筛选，运行与基线分别判断；最新结果未入图不将旧成绩提升为最新。总览默认不显示 Thinking 曲线。仅悬停、聚焦或选中时，才以实线连接同一已记录批次、精确请求模型、题库范围、渠道和账号内至少两个不同的可见 Thinking。批次未知或同档位重复时不补造连线；单档位批次、跨批次的最新点均不连接，筛选和缩放也不补入隐藏记录来凑线。图例查找只高亮点，不展开未选中的曲线。帕累托前沿保持虚线。帕累托前沿按所选轴的可见无异常合格点计算，不因 Thinking 或协议不同而禁用；完整基线仍独立严格校验。默认按模型跨渠道去重，只显示简短模型名，优先以选中点作锚点；渠道和账号仍在图例及数据点详情中保留。标注数量随绘图区宽度控制，最多六个；放不下的名称留在详情中，不挪到远处或增加长引线。桌面画布高 400px，窄屏保留 380px，两者都保留完整 0-100 分轴。实心和空心标记的可见外沿尺寸一致，均含 1.5px 系列色描边：圆点直径 12px，方块边长 10px。最新与历史仅以填充区分。单独的背景色分隔层保持密集点之间的间隔，不再让历史点边框显得比实心点大。点击热区及焦点环保持不变。悬停或聚焦数据点时突出有效的可见同批系列，并展示其可见 Thinking 档位，标签引线逐一对应各自的数据点；展开系列时隐藏静态名称以免叠字。悬停信息使用浮动卡片，自动避开高亮曲线及 Thinking 标签，不再作为整图下方的信息栏；卡片同时展示每轮费用、Token、耗时及查看者本地时间。点击数据点可固定浮动卡片并在下方展开详情，按 Esc 或点击空白处取消固定。滚轮可在指针处缩放，缩放后可拖拽平移，双击复位视图。重叠点保留真实坐标和每条记录，最多列出三个时间，更多记录只显示时间范围与记录次数。点选结果详情仍在图表下方就地展示。移除独立的“查看结果”下拉框；点击图中数据点查看详情，未完成证据仍在任务历史中查看。费用、Token 和耗时轴均绘制帕累托前沿；只有一个最优点时绘制向右延伸的水平边界。不提供全屏按钮。

## UI 接口

全部接口沿用 `X-Mini-Bench-Token`、loopback Host 和同源检查，不允许通过请求体添加任意上游或密钥。

| 方法 | 路径 | 返回 |
| --- | --- | --- |
| GET | `/api/bench/routes` | `{"routes": [...]}`，脱敏的路由目录；`?refresh=1` 重新读取目录 |
| GET | `/api/bench/quota-cards` | 只读额度卡片，状态为 `available`、`forbidden`、`unavailable` 或 `stale`；`?refresh=1` 重读 Magpie 已缓存的卡片，不触发供应商额度刷新 |
| GET | `/api/bench/banks` | `{"banks": [...]}`，题卡与评分策略 |
| POST | `/api/bench/task-plans` | 完整题库的任务计划、独立运行数、样本数及总费用上限，不执行 |
| POST | `/api/bench/tasks` | HTTP 202，`{"id": "..."}`，返回任务 ID |
| GET | `/api/bench/tasks` | `{"tasks": [...]}`，含子运行进度的任务摘要 |
| POST | `/api/bench/tasks/:id/retry` | 手动重试失败、超时、已中断或已取消样本，请求体为 `{request_id}`，返回获准及被拒绝的子运行 |
| POST | `/api/bench/runs/:id/retry` | 手动重试失败、超时、已中断或已取消样本，请求体为 `{request_id}`；显式 `{request_id, policy:"sample-timeout-v1"}` 则按当前仅超时策略补跑全部未完成样本，保留原计划及成功结果 |
| GET | `/api/bench/tasks/:id` | 任务计划及子运行的 ID、身份、状态和预算 |
| POST | `/api/bench/tasks/:id/cancel` | `{"ok": true}`，取消全部未完成的子运行 |
| POST | `/api/bench/plans` | 直接运行的规范化计划和样本数，不执行 |
| POST | `/api/bench/runs` | HTTP 202，`{"id": "..."}` |
| GET | `/api/bench/runs` | `{"runs": [...]}` |
| GET | `/api/bench/runs/:id` | 单次运行、样本和预算状态 |
| GET | `/api/bench/runs/:id/calls` | 从运行及重试日志中只读提取逐次调用诊断：HTTP 状态、耗时、终止事件、上游错误码与消息（截断）、本地超时及是否返回用量。不返回请求正文或原始流 |
| POST | `/api/bench/runs/:id/cancel` | `{"ok": true}`，不存在时 HTTP 404 |
| GET | `/api/bench/observations` | `{"etag": "...", "observations": [...]}`，逐目标、逐题、逐轮分析记录，由 UI 计算已定义的展示指标。带 `?known=ETAG` 且数据未变时返回 `{"etag", "unchanged": true}`。客户端发送 `Accept-Encoding: gzip` 时，2 KB 以上的 JSON 响应会 gzip 压缩 |
| GET | `/api/bench/baselines` | `{"baselines": [...]}`，通过校验的个人基线 |
| POST | `/api/bench/runs/:id/baseline` | 请求 `{"target_id": "..."}`，返回 HTTP 201 和 `{"baseline": ...}` |

运行摘要及任务的子运行摘要包含只读的 `result_quality`，仅统计已完成样本：`completed_samples`、`unscored_samples`、`unknown_usage_samples`、`unknown_cost_samples`、`prior_unknown_usage_samples`、`prior_unknown_cost_samples`。这些计数不改变执行状态、已保存证据、评分或入图资格。

保存基线要求完整 12 题、全部预定轮次完成且可评分、任务与执行协议证据一致。个人基线保存到数据目录的 `mini-bench.sqlite`，不覆盖原运行。查看已有个人运行和已通过校验的基线无需重新发模型请求。来源不兼容的运行不能提升为基线。

计划和启动使用相同请求结构。`GET /api/bench/banks` 同时提供两套正式题库：`assessment-2.0`（`bank_version: "2.0"`，Web 界面默认选中）与 `assessment-1.0`（`bank_version: "1.0"`，CLI/API 省略 `bank_version` 时的回退默认值）。分析图表、任务历史与基线均按 `bank_version` 严格隔离。

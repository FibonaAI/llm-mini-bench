# Bench with Internal Account Routes

[中文](BENCH_EXECUTION.zh.md)

Create separate routes for two accounts with the same provider, then compare them using the same model, bank, and Thinking setting. Routes live in Bench's own configuration file. They do not create or modify Magpie providers or switch the global signed-in account. The CLI and `/api/bench/` share one background scheduler.

## Use Magpie models directly

In the Magpie plugin, when `MAGPIE_BENCH_ROUTES_FILE` is unset and the data directory has no `routes.json`, the adapter generates test targets from the host Magpie model catalog, reusing the host gateway address and credentials. There is no need to configure each model manually. Only models with explicit, finite, nonnegative input and output token prices are listed. Missing prices are not treated as free. Thinking levels come from the model catalog.

When the catalog supplies valid `owned_by` and `display_name` fields, public routes retain them as optional `provider_id` and `model_display_name`, with `provider_evidence: "gateway_catalog"` for the provider claim. `provider_id` identifies the catalog owner instance, not its provider type or the upstream provider that ultimately serves a request. Distinct instance IDs remain separate even when they offer the same model. The UI does not split model IDs or labels to infer identity, and uses neutral icons because the public catalog does not supply authoritative provider types or icons. Plans and results preserve the recorded metadata; historical observations with no recorded fields return `null` and are never backfilled from the current catalog. Explicit route configuration keeps its existing strict schema and requires no new metadata fields.

Automatically allocated targets share the `gateway-default` concurrency pool and use `gateway_binding` evidence. For local (non-remote) Magpie providers, the plugin automatically discovers named accounts and multi-key entries on the receiving gateway (`gateway_account_binding`) and also supports overriding or extending them via its [`accounts` option](../magpie/README.md#local-account-and-multi-key-bindings) (`configured_binding`). The adapter supplies the `X-Magpie-Account` pin header; remote quota cards never become pins. Standalone Bench uses explicit routes and does not implicitly connect to Magpie.

The adapter caches models for up to 60 seconds and coalesces concurrent reads. Refreshing routes invalidates that cache. Removed models can no longer resolve, while started runs retain their original bindings and snapshots. Catalog failures do not prevent opening historical results or cancelling runs. Reading the catalog sends no model requests. Duplicate model IDs cause an error rather than silently selecting prices.

Explicit route configuration always takes precedence. If the file contains `{"routes": []}` or an explicitly specified file does not exist, the target list stays empty; the service does not fall back to the default gateway. An empty path environment variable or malformed file causes an error. Keys stay on the server; the UI receives neither upstream addresses nor credentials.

### Remote Magpie route expansion

The picker automatically separates routes behind Remote Magpie when the catalog supplies valid `magpie_via` evidence. It requests that evidence with the supported `X-Magpie-Drawers: 1` catalog header, then excludes the extra image and other non-chat models returned by that handshake.

For a direct remote entry such as `office/openai/model`, the channel column shows `office / openai`. `office` remains the local catalog owner; `openai` is the first remote **route namespace**, not verified provider identity. Remote `auto` and `group` namespaces are labeled as automatic routes and routing groups. Different local remote instances never merge, even when their inner namespaces match. Expansion is one level only; remaining slashes may be part of a model name and are not recursively interpreted.

Public routes, plans, and new results retain `remote_route: {"namespace": "openai", "evidence": "magpie_via_catalog"}`. The full request model and route ID are unchanged, and accounts remain unknown. Missing or invalid hop evidence, local routing groups, and older records without the metadata keep their original grouping. No historical record is backfilled. Per-process hop IDs are not saved as stable identity. See Magpie's [remote routing convention](https://usemagpie.ai/docs/remote).

The task picker shows the provider, recorded or pinned account, model and Thinking levels. It does not display or fetch quotas in the browser. Remote and unpinned routes keep account identity unknown, and historical results are never backfilled.

## Configure two routes

See [`benchmark/examples/bench-routes.json`](../benchmark/examples/bench-routes.json). Copy it to `~/.local/share/magpie-mini-bench/routes.json`, or set `MAGPIE_BENCH_ROUTES_FILE` in the service process to another file. Recommended file permissions are `0600`. Route configuration loads on first access to the execution service. Restart the service after changing it.

Each route binds these fields:

| Field | Meaning |
| --- | --- |
| `id` | Stable route ID referenced by execution plans |
| `label` | Display name, not evidence of account verification |
| `account_ref` | Stable identifier for a shared account concurrency pool; models using the same account should share this value |
| `base_url` | Upstream address supporting the Responses API, either a direct provider endpoint or an account-scoped gateway |
| `model` | Exact model name sent upstream |
| `api_key_env` | Name of a key environment variable in the service process; plaintext keys are not accepted in the configuration file |
| `thinking_levels` | Locally declared supported levels; an empty array means the UI offers only `default` |
| `pricing.prompt` / `pricing.completion` | USD per input/output token, not per million tokens |
| `account_concurrency` | Sample concurrency limit shared by this account across all Bench runs |

Replace the example addresses, models, prices, and Thinking levels with real values. For example, if input costs USD 1 per million tokens, set `pricing.prompt` to `0.000001`. Use zero only for a confirmed free price, not an unknown price.

The two accounts use `BENCH_PROVIDER_ACCOUNT_A_KEY` and `BENCH_PROVIDER_ACCOUNT_B_KEY`, respectively. These variables must exist in the backend process environment. Setting them only in the terminal that launches the CLI does not pass them to an already running plugin. Do not put keys in plans, project files, or command arguments.

Remote upstreams must use HTTPS; HTTP is allowed only for loopback. Model requests do not follow HTTP redirects. Only `/v1/responses` is supported, with no automatic fallback to Chat Completions or another account.

### Account binding does not verify upstream identity

`account_ref` is an identity you configure, not an account inferred from model answers. Execution results use `configured_binding` to describe the binding source; they do not mark it as verified. Two keys for the same real account should share an `account_ref`. Use different names only for different accounts.

If the upstream is still a gateway that automatically rotates accounts, two local routes do not turn it into a fixed-account gateway. A local Magpie account can instead be pinned through the plugin's explicit `accounts` option. For another gateway, use its supported account-scoped credentials or adapter. Entering an email address as `account_ref` alone does not establish a binding. This version does not automatically sign in, issue Magpie keys, or verify actual upstream accounts. Response IDs and raw responses are retained for later checks.

## Tasks and independent runs

A task is a batch of independent runs. Each selected route and Thinking combination creates one run with its own ID, progress, budget, samples, and results. A route supplies the provider/account/model binding; selecting a label cannot strengthen its identity evidence. Each run executes the complete Mini Bench bank. Defaults are 3 rounds, 6 concurrent samples per run, and 3 concurrent runs per task. Seven selected combinations therefore produce 7 runs, 36 samples each, and 252 samples in total.

```json
{
  "bank_version": "1.0",
  "targets": [
    {"route_id": "provider-a-model-x", "thinking": "none"},
    {"route_id": "provider-a-model-x", "thinking": "high"}
  ],
  "rounds": 3,
  "sample_concurrency": 6,
  "run_concurrency": 3,
  "limits": {"timeout": 600, "timeout_scope": "sample"}
}
```

Save this structure as a task plan, then use `task-plan FILE` to review it and `task-start FILE` to submit it. `tasks`, `task-show TASK_ID`, and `task-cancel TASK_ID` manage the batch. `show RUN_ID` and `cancel RUN_ID` inspect or cancel an individual child run. Both CLI and UI use the same in-process engine; no CLI subprocess is launched per run.

New tasks default to `timeout: 600` and `timeout_scope: "sample"`; `max_requests`, `max_output_tokens`, `max_cost_usd`, `max_turns` and `max_tool_calls` are `null` (uncapped). The timeout covers each entire question across tool continuations and retries, not a fresh allowance per HTTP call. `total_max_cost_usd` is `null`. Historical records without `timeout_scope` retain their original per-request timeout and recorded numeric limits; neither plans nor provenance hashes are rewritten. Tasks have no additional aggregate sample-count cap. Each task manages its own `run_concurrency` and `sample_concurrency` independently, spreading concurrent child runs across channels and models, with budgets enforced per run. Tasks do not accept `task_ids`; subset execution remains available only through the direct run API below. After a submission timeout, inspect `tasks` and `runs` before submitting again.

Task membership is committed before any child can dispatch. Each child keeps its own run snapshot and journal; `assessment/tasks/<task_id>/task.json` records membership. Cancellation can target one child or the whole task. Restarted unfinished work is interrupted, never resumed. Existing multi-target run records remain readable without conversion into new tasks.

## Preflight and direct runs

Start the backend through the plugin installation described in the [README](../README.md). For explicit account routes, finish configuration and environment-variable setup before starting or restarting it. Do not run multiple processes against the same data directory. Concurrency allowances are not shared across processes either.

Run the following CLI commands from the repository root. The CLI connects to an already running local service at `http://127.0.0.1:3481` by default. Change the address with `--url` or `MAGPIE_BENCH_URL`, and authenticate with `MAGPIE_BENCH_TOKEN`.

```sh
bun benchmark/bench.ts routes
bun benchmark/bench.ts banks
bun benchmark/bench.ts plan benchmark/examples/bench-plan.json
bun benchmark/bench.ts start benchmark/examples/bench-plan.json
bun benchmark/bench.ts runs
bun benchmark/bench.ts show <run_id>
bun benchmark/bench.ts cancel <run_id>
```

[`benchmark/examples/bench-plan.json`](../benchmark/examples/bench-plan.json) includes two accounts, each running both `none` and `high`. One round of all 12 tasks produces 48 samples. Omitting `task_ids` selects the complete bank. You can also explicitly select a few tasks to check configuration:

```json
{
  "bank_version": "1.0",
  "targets": [
    {"id": "a-high", "route_id": "provider-a-model-x", "thinking": "high"},
    {"id": "b-high", "route_id": "provider-b-model-x", "thinking": "high"}
  ],
  "task_ids": ["K23_HTTP_Conditional_Cache_Precedence"],
  "rounds": 1,
  "concurrency": 2,
  "limits": {"timeout": 600, "timeout_scope": "sample"}
}
```

`plan` validates configuration, credential references, and execution size without sending model requests. `start` validates again, saves a snapshot, and immediately returns a run ID. Execution does not depend on keeping the CLI open. A submission timeout does not prove that no run was created. Check `runs` before submitting again. There is currently no submission deduplication key.

Target `thinking` is optional: omitted or `default` sends no `reasoning` and differs from explicit `none`; any other value must be advertised by the route and is sent as `reasoning.effort`; `mixed` and `unknown` are reserved. New plans use only `timeout` and `timeout_scope: "sample"`; nullable legacy cap fields remain readable for historical records and explicit legacy API clients. Thinking levels for explicit routes come from local declarations; default gateway routes use the catalog. Neither probes capabilities through model requests.

### Run without the plugin

The TypeScript backend and web interface live in `benchmark/` and can run with Bun without the Magpie adapter. Set `MAGPIE_BENCH_TOKEN` to a random string of at least 32 characters in the service process environment. Configure explicit routes and their key environment variables if you are not using the Magpie gateway. From the repository root, start:

```sh
bun benchmark/bench.ts serve --port 3481
```

The service serves `benchmark/web/` and the same HTTP API. The CLI still uses `MAGPIE_BENCH_TOKEN` to authenticate. Do not start this service alongside an active plugin using the same port or data directory. Use a managed tmux task with an explicit completion or failure notification for persistent operation.

## Scheduling and results

All Bench tasks and runs share one scheduler. Each task manages its own `run_concurrency` (1 to 10, default 3) and `sample_concurrency` (1 to 64, default 6) independently without queueing behind other tasks. A task child can run several samples of its fixed target concurrently, and child runs are interleaved across channels and models so concurrent slots spread across distinct channels and models rather than bunching on one channel's Thinking levels. Direct runs created through `/runs` share `MAGPIE_BENCH_CONCURRENCY` (1 to 64, default 18), per-account concurrency limits (shared across models and Thinking settings on the same account), and the per-target limit of one sample. Available slots are filled with runnable samples without waiting for an entire batch to finish.

A sample corresponds to a target, task, and round. Multiple requests for a tool task execute sequentially within that sample, and tool state is not shared across samples. Samples and actual attempts have separate saved IDs, so the same model on different accounts does not overwrite results. Raw responses are saved before grading. API failures and missing or ungradable outputs are not scored as zero. Whole-sample timeouts (`SampleTimeout`) score `0` and let the run finish as `completed` while staying retryable. The analysis page derives only the [defined score-cost display](ASSESSMENT_BANK.md#score-cost-display) from eligible records; it does not change saved grades.

New tasks count every request for evidence but impose only the complete-sample deadline, shared by calls, tool continuations and retry waits. Saved legacy runs still enforce their recorded per-run request and USD limits on manual retries. Transient transport errors, HTTP 408/429/5xx, and HTTP 200 streams that end in `response.failed` with error code `server_error` (such as a gateway losing its connection mid-reply) or a rate-limit/quota code (`rate_limit_exceeded`, `insufficient_quota`, handled like HTTP 429) retry up to `max_api_retries` (default 3, in addition to the initial request), with exponential backoff and bounded Retry-After handling. Permanent authentication/other 4xx failures are not automatically retried. Fast-fail: when a sample ends as an API failure (or an upstream abort after a valid submission) whose last response was HTTP 429 or a streamed `response.failed` with `rate_limit_exceeded`/`insufficient_quota` (`rate_limited`), 401/403 (`access_denied`), 402 (`payment_required`) or 404 (`model_not_found`), no new sample of that route (same model and account binding) starts anywhere in the service: not in the same run, sibling Thinking runs, other concurrent tasks, or tasks created later. Samples already in flight finish normally, and other routes — including other accounts and automatic routing groups, which have their own route IDs — are unaffected. One such sample is enough. Because in-sample API retries already absorb transient errors, blocks never expire on their own: every block lasts until an explicit manual retry of a run on that route (which clears the block) or a service restart. Unsent samples stay `budget_not_admitted` with that stop reason, never score zero, and remain manually retryable. Timeouts, 5xx and transport errors never trigger fast-fail. Capability/output/tool/turn limits are `incomplete`, not API failures; exhausted API errors are `api_failure` samples and `failed` runs. Missing usage/cost remains null and retains a conservative cost reservation, rather than stopping every later sample solely because an error omitted usage. Tool requests omit `parallel_tool_calls`. Multiple function calls in one response are validated for unique call IDs, then executed against fixed simulators in returned order; every result is journaled and all matching outputs are sent back together. Cancellation, sample deadline and storage failure stop remaining actions. This execution change is recorded in execution source snapshots and `tool_execution_policy: "ordered-batch-v1"`; old calls/results are not rewritten. Accounts never switch. An upstream gateway may retry internally; the Magpie gateway currently does not expose a verified way for this plugin to disable every such retry. Do not interpret one recorded gateway request as proof of one upstream attempt.

Assessment requests use Responses SSE with `stream: true`, recorded in each request protocol and its hash. Complete SSE frames are journaled before parsing, tool execution or grading. Each `stream_chunk` row carries only its call ID, sample ID, attempt ID, index, time and frame text. When the chunks reproduce the received stream byte for byte, the call record stores `raw_stream_chunks: N` instead of a second copy (`journal_raw_response_text` rebuilds it); otherwise, for example after an abort or an HTTP error body, it keeps `raw_response_text`. Older journals keep their original layout. Call records retain the HTTP status, first/last byte times, first event/output times, last output progress and terminal event. Heartbeats do not count as output progress. Only a complete terminal response supplies the answer, tool calls and usage; early EOF, invalid SSE and a successful non-SSE response are protocol exceptions, with no silent downgrade to non-streaming. Streaming can avoid gateway idle timeouts when events reach the client, but does not override gateway total-duration limits. Neither local `SampleTimeout` nor an active stream establishes that a model spent the whole deadline computing. Historical records retain their original transport provenance.

Cancellation blocks samples that have not started and subsequent tool requests, and aborts an in-flight stream. An abort does not prove upstream work stopped or prevent charges; already received evidence is retained where possible. Interrupted runs do not automatically resend requests after a service restart. Terminal failed, timed-out, interrupted, cancelled, or retry-eligible `budget_not_admitted` samples can be retried explicitly through the run or task retry endpoint with a required 32-character lowercase hexadecimal `request_id`. Reusing the ID is idempotent, including after an uncertain HTTP response. Prior run bytes, raw calls and source snapshots are archived; completed samples do not rerun, retried samples retain prior attempts in `attempts`, the latest result replaces the failed result rather than selecting best-of, and when the latest attempt completes with known usage and cost those values become the sample's effective usage and cost. Original route/account identity, prices and remaining limits must still match. Results, task summaries and analysis refresh after retry. Retried runs remain eligible for baseline promotion when every retry batch preserves current bank/grader/simulator source hashes, protocol limits and execution policy without changing per-sample protocol identity; retries that change limits, rerun policy, or bank sources remain for analysis only.

Workspace state — tasks, runs, samples, immutable attempt histories, compact Pi Session-style `session_events`, content-deduplicated snapshots, and personal baselines — lives in a single private SQLite database (`mini-bench.sqlite`, WAL mode) under the data directory. Raw SSE stream chunks and per-run `source/*.ts` file copies are not written. The HTTP service also caches serialized and gzip-compressed payloads for `/api/bench/banks`, `/api/bench/tasks`, `/api/bench/runs`, `/api/bench/observations`, and terminal `/api/bench/runs/:id` detail responses (bounded LRU, invalidated on status/`updated_at` changes); `/api/bench/tasks/:id` and `/api/bench/runs/:id` accept `?omit_provenance=1` to skip immutable bank/task/source snapshots when UI callers only render progress and sample results.

On a storage write failure, the service stops admitting new requests, releases concurrency slots for samples that have finished, and records `storage_error` in memory. If the disk is unwritable, saving that error cannot be guaranteed. On restart, the service marks runs as interrupted based on the last successfully saved state. Fix storage and restart before submitting new runs; do not try to bypass the failure with repeated submissions.

New execution source snapshots include the runner and its local import dependencies, including modules imported unconditionally by the bank loader even when their tasks are not selected. Source paths resolve relative to `benchmark/`. This archive coverage does not change bank hashes, grading or historical snapshots.

Results are saved under `assessment/` in the data directory. They include questions, answers, and tool traces and should be treated as sensitive data. The service does not return keys, key environment-variable names, or upstream addresses to the UI. Known credential literals in raw upstream content are redacted, so saved responses are not guaranteed to be byte-for-byte copies of network messages.

Only Mini Bench is used here. The old runner and bank APIs have been removed. Retired-bank personal data is not automatically read, converted, or deleted. Historical Mini Bench runs in `assessment/` remain visible with their recorded provenance.

## Analysis and task pages

The analysis page centers on the score-cost chart. Search and multi-select channel, model, and Thinking filters directly update the chart: choices within a filter are combined with OR, and different filters are combined with AND. An unrestricted filter includes all values. Active conditions can be removed individually; "Only this" selects one value within its filter. Source filtering applies alongside these conditions. "Latest" is the default: within each bank and whole/subset scope, it selects the newest recorded timestamp for each channel/account/model/Thinking combination, separately for runs and baselines. Selection precedes chart eligibility, so an incomplete latest result is reported as excluded rather than replaced by an older score. Undated observations remain visible because their recency cannot be established. "All history" shows all records, including the latest; "Selected records" uses exact record checkboxes. Both historical modes support inclusive local-calendar date bounds. Filtering does not delete history, combine repeated evaluations or change metrics. The "Data" dropdown sits beside the channel/model/Thinking filters; its panel contains the latest/all/specified choices, date bounds and exact record checkboxes rather than adding a separate form below the toolbar. Matching-record and exclusion counts open bounded panels beside their triggers, with internal scrolling and immediately visible reasons instead of requiring a scroll past the chart. Escape and the close action restore focus to the trigger; outside clicks dismiss the panel. Native Popover and CSS anchors are used when supported, with viewport-clamped manual positioning for older browsers and tight host windows. The analysis floating panels share 8px padding, a compact title row and completion or close actions. Channel, model and Thinking filters use 320px, 340px and 240px widths respectively; data selection uses 340px and chart settings use 280px, all clamped to the viewport. Chart settings share the same Escape, outside-click and focus-return behavior as data selection. Both record panels share a 440px width and 360px maximum height, shrinking further to fit the viewport. Compact rows retain model/Thinking, recorded channel and known account claims, local time, score and known usage; only excluded rows add a reason. Long record IDs, unknown-account boilerplate and repeated missing-usage labels stay out of the list and remain available in the inspector. Dates include the year when needed to distinguish years, and full timestamps remain accessible. Tasks and analysis share identity normalization and search over recorded model, channel, and account fields. The task picker selects exact runnable targets, retains selections when its candidate filters change, and closes with "Done". Model options in the task picker follow the selected channel, retaining a compatible model filter or resetting it to all models. Accounts remain visible and searchable without a separate account filter. Routes with advertised levels offer only those explicit levels; routes without levels offer a single "Default" option, whose requests omit `reasoning`. The inspector retains per-task results and raw details. Task history is searchable and filterable on the task page, filtering both tasks and matching child runs inside an expanded task, with inline run preview cards and lazy JSON expansion for raw details. There is no independent question-bank page. The UI automatically updates sample counts and the combined budget as targets or settings change. Click "Start evaluation" once to submit; the server validates the configuration before execution, and the target picker resets selection and filters afterward. No separate planning action is required. The only execution-limit field is the whole-sample timeout, default 600 seconds, covering requests, tool interactions and retry backoff together. Output tokens, request counts, USD, tool calls and turns are uncapped. Transient API retries default to 3 internally. A sample timeout ends only that sample (scoring `0`); other samples continue. Copying an old task into a new task uses this new execution policy rather than silently reinstating its old caps. Task and child-run details expand inline, with status counts, configuration copying, baseline promotion or removal (at the whole-task header, per-channel pod and multi-model group headers when actionable runs exist, and inside the expanded child-run detail for individual Thinking/account runs — including healthy subsets inside abnormal tasks, automatically skipping ineligible or timed-out runs, preserving underlying run records, and explaining ineligibility in the task and run detail headers), and explicit manual retry actions for failed, timed-out, interrupted or cancelled samples. Copying only restores currently available exact targets and settings; it never starts requests. After an uncertain submission, review task history and explicitly acknowledge that review before submitting again.

Task and standalone-run cards toggle open and closed on repeated clicks. A child-run row, including its status, toggles that child's samples without closing its parent; cancellation buttons do not toggle details. Opening a run from analysis always opens it rather than toggling it closed. Polling preserves expanded samples, nested evidence disclosures and keyboard focus, and does not reopen an explicitly closed card.

Execution completion, grading validity and usage accounting are separate. Completed samples with `ambiguous` or `ungradable` outcomes show why they cannot be scored, rather than implying grading is pending. Ambiguity may come from different candidate JSON objects or malformed extra JSON; the UI does not choose one, regrade the answer or replace a missing score with zero. Zero is a valid score. Run summaries flag completed samples with invalid scores or unknown usage/cost. When a retried sample completes with known usage and cost, those effective values are used while prior attempts remain archived; samples whose effective usage or cost remains unknown are counted for lower-bound presentation.

The X-axis selects estimated USD, input plus output tokens, or elapsed time per complete 12-task round. Eligibility requires complete valid scores and known nonnegative usage or duration for that axis; missing USD does not exclude a record from the token or duration axis if that axis value is known. Attempts that sent no request count as known zero usage. When scores are complete but some attempts returned no usage, the "Plot incomplete usage at known lower bound" chart setting (on by default) plots the known lower bound. The excluded list names concrete causes (API failures, ambiguous answers, unknown-usage attempts, interrupted or cancelled samples) and links retryable runs to the task page for manual retry. Run details show a task-by-round matrix, list samples needing attention first, and show per-attempt failure causes read from `/api/bench/runs/:id/calls`. Changing coloring does not merge observations, alter eligibility or expand Thinking lines. The color legend shows one compact row below the plot. Unknown batch membership or duplicate effort levels do not invent a series. Single-level batches and cross-batch latest points never connect; filters and zoom do not add hidden records to complete a line. Legend lookup highlights points without revealing unselected curves. The Pareto frontier remains dashed. The frontier uses visible eligible non-anomalous points on the chosen axis and is not gated on Thinking/protocol equality. Strict baseline validation remains separate. Default labels show a short model name once across channels, preferring a selected point as its anchor; channel/account identities remain in the legend and point details. Desktop charts use a 400px canvas, while narrow charts retain 380px; both preserve the full 0-100 score scale. Only the fill distinguishes latest from historical records. A separate background-colored halo keeps dense points apart without enlarging historical outlines relative to filled points. Hit areas and focus rings are unchanged. Crowded identities remain available through point details and the existing data selector. ## UI API

All endpoints retain `X-Mini-Bench-Token`, loopback Host, and same-origin checks. Request bodies cannot add arbitrary upstreams or keys.

| Method | Path | Response |
| --- | --- | --- |
| GET | `/api/bench/routes` | `{"routes": [...]}`, a redacted route catalog; `?refresh=1` reloads the catalog |
| GET | `/api/bench/quota-cards` | Read-only quota cards with available, forbidden, unavailable or stale status; `?refresh=1` rereads Magpie’s cached cards without requesting a vendor quota refresh |
| GET | `/api/bench/banks` | `{"banks": [...]}`, task cards and grading policy |
| POST | `/api/bench/task-plans` | Whole-bank task plan, independent run count, sample counts, and total cost limit; does not execute |
| POST | `/api/bench/tasks` | HTTP 202, `{"id": "..."}`, the task ID |
| GET | `/api/bench/tasks` | `{"tasks": [...]}`, task summaries with child run progress |

Run summaries and task child summaries include a read-only `result_quality` projection over completed samples (`completed_samples`, `unscored_samples`, `unknown_usage_samples`, `unknown_cost_samples`, `prior_unknown_usage_samples` and `prior_unknown_cost_samples`) plus baseline state (`baseline_eligible`, `ineligibility_reason`, and `baseline_id`). These fields do not change execution status, saved evidence, grades or chart eligibility.

Saving a baseline requires all 12 tasks, completion and gradability of every planned round, and consistent task and execution protocol evidence. Personal baselines are saved in `mini-bench.sqlite` under the data directory without overwriting the original run. Viewing existing personal runs and accepted baselines requires no new model requests. Runs with incompatible source provenance cannot be promoted to baselines.

Planning and starting use the same request structure. `GET /api/bench/banks` serves both official banks: `assessment-2.0` (`bank_version: "2.0"`, default in the web UI) and `assessment-1.0` (`bank_version: "1.0"`, default when CLI/API requests omit `bank_version`). Analysis views, task histories, and baselines are strictly isolated by `bank_version`.
